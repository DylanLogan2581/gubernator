# Deployment Runbook

Step-by-step guide to bring up a fresh Gubernator environment from scratch.
Covers production (self-hosted Supabase via Docker Compose) and local
development (Supabase CLI).

---

## Production (self-hosted, Docker Compose)

Everything — Postgres, the full Supabase stack, edge functions, database
migrations, and the React app — runs from one compose file in `docker/`.

### Prerequisites

- A Linux server with [Docker Engine](https://docs.docker.com/engine/install/)
  and the Docker Compose plugin (`docker compose version` works)
- At least 2 CPU cores and 4 GB RAM recommended
- An SMTP provider for magic-link email delivery (SendGrid, Postmark, Resend, …)
- (Recommended) A domain with two hostnames pointed at the server, e.g.
  `app.example.com` (React app) and `api.example.com` (Supabase API), fronted
  by a TLS reverse proxy such as Caddy or nginx

### Deploy in 4 steps

```bash
# 1. Get the code
git clone <this-repo-url> gubernator && cd gubernator/docker

# 2. Create the env file and generate all secrets
cp .env.example .env
sh generate-keys.sh --update-env

# 3. Edit .env — set the URLs, CORS origins, and SMTP block (see tables below)
$EDITOR .env

# 4. Build and start everything
docker compose up -d --build
```

That's it. On startup the `migrate` service applies every file in
`supabase/migrations/` (idempotently — it re-runs safely on every `up`), and
the edge functions are served straight from the repo checkout. There is no
separate `db push` or `functions deploy` step.

### Variables you must edit in `.env`

| Variable                                                                                                                | Set to                                                                                                                                                                      |
| ----------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `SUPABASE_PUBLIC_URL`                                                                                                   | Public URL of the Supabase API (Kong), e.g. `https://api.example.com`. The app is built against this value.                                                                 |
| `API_EXTERNAL_URL`                                                                                                      | Same as `SUPABASE_PUBLIC_URL` (used in magic-link emails / OAuth callbacks)                                                                                                 |
| `SITE_URL`                                                                                                              | Public URL of the React app, e.g. `https://app.example.com`                                                                                                                 |
| `END_TURN_SIMULATION_ALLOWED_ORIGINS`<br>`ADMIN_CREATE_USER_ALLOWED_ORIGINS`<br>`EXPORT_WORLD_TEMPLATE_ALLOWED_ORIGINS` | The app origin (`https://app.example.com`). Comma-separated for multiple origins; scheme + host only, no path, no trailing slash. Requests from other origins get HTTP 403. |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`                                                                      | Your SMTP provider credentials                                                                                                                                              |
| `SMTP_ADMIN_EMAIL`, `SMTP_SENDER_NAME`                                                                                  | From-address and sender name for auth emails                                                                                                                                |
| `DASHBOARD_USERNAME`                                                                                                    | Login name for the Supabase Studio dashboard (password is generated)                                                                                                        |

### Variables generated by `generate-keys.sh`

Never commit these; `docker/.env` is gitignored.

| Variable                                   | Purpose                                                                          |
| ------------------------------------------ | -------------------------------------------------------------------------------- |
| `POSTGRES_PASSWORD`                        | Postgres superuser + service-role DB passwords                                   |
| `JWT_SECRET`                               | HS256 signing key shared by all Supabase services                                |
| `ANON_KEY` / `SERVICE_ROLE_KEY`            | API key JWTs (anon / service_role) — `ANON_KEY` is also baked into the app build |
| `DASHBOARD_PASSWORD`                       | Studio dashboard login                                                           |
| `SECRET_KEY_BASE`, `REALTIME_DB_ENC_KEY`   | Realtime encryption                                                              |
| `PG_META_CRYPTO_KEY`                       | Studio ↔ postgres-meta encryption                                                |
| `S3_PROTOCOL_ACCESS_KEY_ID` / `..._SECRET` | Storage S3-protocol endpoint credentials                                         |

### Variables with sensible defaults

| Variable                                                                | Default                         | Notes                                                                                                       |
| ----------------------------------------------------------------------- | ------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| `APP_PORT`                                                              | `3000`                          | Host port of the React app (nginx)                                                                          |
| `KONG_HTTP_PORT` / `KONG_HTTPS_PORT`                                    | `8000` / `8443`                 | Host ports of the Supabase API gateway + Studio                                                             |
| `POSTGRES_PORT`                                                         | `5432`                          | Published on `127.0.0.1` only (server-local admin use)                                                      |
| `POSTGRES_HOST` / `POSTGRES_DB`                                         | `db` / `postgres`               | Leave as-is                                                                                                 |
| `JWT_EXPIRY`                                                            | `3600`                          | Access-token lifetime (seconds)                                                                             |
| `DISABLE_SIGNUP`                                                        | `false`                         | Set `true` to allow only admin-created users                                                                |
| `ENABLE_EMAIL_SIGNUP` / `ENABLE_EMAIL_AUTOCONFIRM`                      | `true` / `false`                | Matches local dev auth config                                                                               |
| `FUNCTIONS_VERIFY_JWT`                                                  | `false`                         | Keep `false` — functions validate JWT + roles themselves; gateway verification would reject CORS preflights |
| `APPLY_SEED`                                                            | `false`                         | `true` seeds deterministic test users/worlds — dev stacks only                                              |
| `PGRST_DB_SCHEMAS`                                                      | `public,storage,graphql_public` | Schemas exposed via REST                                                                                    |
| `STUDIO_DEFAULT_ORGANIZATION` / `_PROJECT`                              | `Gubernator`                    | Studio display names                                                                                        |
| `GLOBAL_S3_BUCKET`, `REGION`, `STORAGE_TENANT_ID`, `IMGPROXY_AUTO_WEBP` | `stub`/`stub`/`stub`/`true`     | Storage backend settings (file-backed)                                                                      |

### Ports and services

| Host port                           | Service                                                                                                                                             |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `${APP_PORT}` (3000)                | React app (nginx, container port 8080)                                                                                                              |
| `${KONG_HTTP_PORT}` (8000)          | Supabase API gateway — auth, REST, realtime, storage, edge functions — and Studio dashboard (basic-auth: `DASHBOARD_USERNAME`/`DASHBOARD_PASSWORD`) |
| `${KONG_HTTPS_PORT}` (8443)         | Same, TLS (self-signed unless you mount certs)                                                                                                      |
| `127.0.0.1:${POSTGRES_PORT}` (5432) | Postgres — loopback only, for `psql` / `supabase db push` from the server                                                                           |

All other services (auth, rest, realtime, storage, imgproxy, meta, functions,
studio) are internal to the compose network and reached through Kong.

For TLS, put a reverse proxy (Caddy, nginx, Traefik) in front:
`app.example.com → localhost:3000` and `api.example.com → localhost:8000`,
then use the `https://` URLs in `.env`. **Do not expose Kong or the app over
plain HTTP on the public internet.**

### Bootstrap the first superadmin

1. Open the app (`SITE_URL`), sign in via magic link with your email. This
   creates the auth user and its `public.users` profile row.
2. Promote it (run on the server):

   ```bash
   docker compose exec db psql -U postgres -d postgres -c \
     "update public.users set is_super_admin = true \
      where id = (select id from auth.users where email = 'you@example.com');"
   ```

3. Reload the app — `/superadmin/` is now accessible. Create further users
   from there (see `docs/admin-operations.md`).

### Updating a deployment

```bash
cd gubernator && git pull
cd docker && docker compose up -d --build
```

- New migrations are applied automatically by the `migrate` service.
- Edge function changes are picked up from the checkout; if a function was
  already warm, restart it: `docker compose restart functions`.
- App changes are rebuilt into the `app` image by `--build`.

### Operations

| Task                       | Command (from `docker/`)                                           |
| -------------------------- | ------------------------------------------------------------------ |
| Logs                       | `docker compose logs -f [service]`                                 |
| Migration status           | `docker compose logs migrate`                                      |
| Re-run migrations          | `docker compose up migrate`                                        |
| Psql shell                 | `docker compose exec db psql -U postgres`                          |
| Backup database            | `docker compose exec db pg_dumpall -U postgres > backup.sql`       |
| Stop / start               | `docker compose down` / `docker compose up -d`                     |
| Full reset (destroys data) | `docker compose down -v && rm -rf volumes/db/data volumes/storage` |

Persistent state lives in `docker/volumes/db/data` (Postgres) and
`docker/volumes/storage` (file storage) — include both in backups.

### Production verification checklist

- [ ] `docker compose ps` shows all services healthy, `migrate` exited `0`
- [ ] App loads at `SITE_URL` and shows the sign-in page
- [ ] Magic-link sign-in delivers an email and completes
- [ ] Studio reachable at `SUPABASE_PUBLIC_URL` with dashboard credentials
- [ ] First superadmin promoted and can reach `/superadmin/`
- [ ] End turn completes without error on a test world

## Local development (Supabase CLI)

### Prerequisites

- [Node.js](https://nodejs.org/) (see `.nvmrc` for the required version)
- [Supabase CLI](https://supabase.com/docs/guides/cli) (`npm install -g supabase` or Homebrew)
- [Docker](https://www.docker.com/) — required for the local Supabase stack

### 1. Install dependencies

```bash
npm install
```

### 2. Configure environment variables

Copy the example file and fill in the values:

```bash
cp .env.example .env
```

| Variable                 | Description                             |
| ------------------------ | --------------------------------------- |
| `VITE_SUPABASE_URL`      | Local API URL: `http://127.0.0.1:54321` |
| `VITE_SUPABASE_ANON_KEY` | anon key printed by `supabase start`    |

(In the Docker production deploy these two are derived automatically from
`SUPABASE_PUBLIC_URL` and `ANON_KEY` at image build time.)

SMTP: leave defaults — the local stack includes
[Inbucket](http://localhost:54324) for catch-all email inspection.

Edge-function CORS allowlists are already set for local dev in
`supabase/config.toml` under `[edge_runtime.secrets]`:

| Variable                                | Function                | Local default                                 |
| --------------------------------------- | ----------------------- | --------------------------------------------- |
| `END_TURN_SIMULATION_ALLOWED_ORIGINS`   | `end-turn-simulation`   | `http://localhost:5173,http://127.0.0.1:5173` |
| `ADMIN_CREATE_USER_ALLOWED_ORIGINS`     | `admin-create-user`     | `http://localhost:5173,http://127.0.0.1:5173` |
| `EXPORT_WORLD_TEMPLATE_ALLOWED_ORIGINS` | `export-world-template` | `http://localhost:5173,http://127.0.0.1:5173` |

No action needed unless you change the Vite dev server port.

### Edge function required env vars (auto-injected)

Each edge function validates these at cold start via `assertEdgeEnvVars` in
`supabase/functions/_shared/http/env.ts`. Both the Supabase CLI (local) and
the Docker compose stack (production) inject them automatically — you do not
set them manually.

| Variable                    | Used by                                                                                      |
| --------------------------- | -------------------------------------------------------------------------------------------- |
| `SUPABASE_URL`              | all functions                                                                                |
| `SUPABASE_ANON_KEY`         | all functions                                                                                |
| `SUPABASE_SERVICE_ROLE_KEY` | `end-turn-simulation`, `admin-create-user`, `export-world-template` (rate-limit bucket only) |

If a required variable is missing at cold start, the function throws immediately
with `"Edge function cold-start failed — missing required env vars: ..."`.

### 3. Start the stack and apply migrations

```bash
supabase start
supabase db reset
```

`db reset` replays every file in `supabase/migrations/` in chronological order,
then runs `supabase/seed.sql` to create deterministic test users and worlds.

After any migration change, regenerate the TypeScript database types:

```bash
npm run db:types
```

Skipping `db:types` after a schema change will leave `src/types/database.ts`
stale and cause build failures.

### 4. Start the dev server

```bash
npm run dev
```

App runs at `http://localhost:5173`.

### Local verification checklist

- [ ] `supabase status` shows all services healthy
- [ ] App loads at `http://localhost:5173` and shows the sign-in page
- [ ] Magic-link sign-in delivers an email to Inbucket
- [ ] A superadmin user can reach `/superadmin/` and see the settings page
- [ ] End turn completes without error on a test world
- [ ] `npm run test:db` passes against the local database

Before a UI review, run `supabase migration list` against the review
environment and confirm it has no unapplied repo migrations — a stale
environment silently reproduces already-fixed bugs (e.g. old notification
text) as phantom reports. Migration filenames use a monotonic
`YYYYMMDDHHMMSS` sequence id, not the actual authoring date, so a filename
dated ahead of "today" is expected and does not indicate drift by itself.

## Local vs production differences

| Concern           | Local                                           | Production (Docker)                                |
| ----------------- | ----------------------------------------------- | -------------------------------------------------- |
| Supabase stack    | `supabase start` (CLI)                          | `docker compose up -d` in `docker/`                |
| Migrations        | `supabase db reset`                             | Auto-applied by the `migrate` service              |
| Edge functions    | Served by CLI from `supabase/functions`         | Served by edge-runtime from the same directory     |
| Seed data         | Auto-applied by `db reset`                      | Off (`APPLY_SEED=false`)                           |
| SMTP              | Inbucket (port 54324)                           | External SMTP provider (`SMTP_*` in `docker/.env`) |
| CORS secrets      | `supabase/config.toml` `[edge_runtime.secrets]` | `*_ALLOWED_ORIGINS` in `docker/.env`               |
| Frontend          | Vite dev server, `http://localhost:5173`        | nginx container at `SITE_URL`                      |
| Anon/service keys | Printed by `supabase start`                     | Generated by `docker/generate-keys.sh`             |
